# Инструкция для ИИ-агента: SiteVSservice

Применяй эту инструкцию при работе с этим репозиторием. Следуй также указаниям пользователя и более приоритетным системным инструкциям. Не предполагай, что другая открытая папка относится к этому проекту.

## Контекст

- Репозиторий: https://github.com/wwdewew1111-ctrl/SiteVSservice.git, основная ветка — `main`.
- Сайт: React, TypeScript и Vite; данные и серверные функции — Supabase.
- Для REG.RU готовая статическая сборка хранится в `reg-ru-site/`. Одного изменения исходников недостаточно: хостинг устанавливает именно эту сборку.
- Каталог сайта по умолчанию: `$HOME/www/kabanyesports.online`. Перед установкой убедись, что путь соответствует хостингу пользователя.
- Подробности: `DEPLOY_REG_RU.md` и `install-reg-ru.sh`; при расхождениях проверяй фактическое содержимое файлов.

## Порядок работы

1. Проверь `git remote -v`, текущую ветку, `git status --short` и соответствующие файлы. Не перезаписывай чужие незакоммиченные изменения. Выясни требования и внеси минимальные изменения, соблюдая стиль проекта.
2. При необходимости установи зависимости через `npm ci`. Запусти `npm run typecheck`, подходящие проверки и `npm run build`; сообщи о любых ошибках. Для изменений интерфейса по возможности проверь результат в браузере.
3. Перед production-сборкой установи `VITE_SUPABASE_URL` и полный `VITE_SUPABASE_ANON_KEY` в окружении сборки. URL проекта указан в `.env.example`; ключ бери из надёжного источника конфигурации проекта или имеющейся проверенной production-сборки, либо запроси у пользователя. Не публикуй значения ключей в ответах и логах. В Vite попадают только публичные publishable/anon-ключи: никогда не используй `service_role`, secret key или FACEIT-ключ и не добавляй `.env` в Git.
4. Внимательно проверь передачу полного ключа: в PowerShell строка `$keys[0]` возвращает первый символ, если `$keys` — строка, а не массив. Проверяй тип и фактическое значение, а не только непустоту. После сборки проверь, что полный ожидаемый ключ и URL присутствуют в фактически подключённом JavaScript-файле `dist/`, а нужное изменение включено в сборку. Не показывай сам ключ.
5. Когда затронут фронтенд или его конфигурация, перенеси содержимое `dist/` в `reg-ru-site/`, включая скрытый `.htaccess`, затем проверь `index.html`, ссылки на существующие ассеты и сами файлы. Не удаляй чужие файлы без необходимости; если сохраняешь старые хешированные ассеты для кэша, убедись, что `index.html` ссылается на новые. Если меняются серверные функции или схема Supabase, одной статической сборки недостаточно: отдельно опиши и согласуй необходимые действия с базой или Edge Functions.
6. Для проверки подключения используй публичный ключ из новой сборки: проверь реальные запросы к таблицам, которые использует главная страница (`src/lib/siteApi.ts`), HTTP-статусы и наличие обязательных записей настроек. Успешная сборка не гарантирует работающую базу. По возможности проверь сайт целиком в браузере, включая `/admin`; не меняй данные при проверке.
7. Если пользователь попросил публикацию либо она явно входит в текущую задачу, проверь diff и статус, закоммить только относящиеся к задаче изменения и отправь в согласованную ветку. Не выполняй force-push. Проверь, что хеш удалённой ветки соответствует опубликованному коммиту. При отсутствии доступа сообщи об этом, не утверждай, что публикация состоялась.
8. Для применения на REG.RU дай пользователю одну команду для Shell-клиента. По умолчанию сохраняй интерактивное подтверждение установщика и предупреди о перезаписи совпадающих файлов и резервной копии. Если пользователь явно согласен на автоматическое подтверждение или интерактивный ввод не работает, можно передать `printf 'YES\n'` в установщик, явно предупредив, что команда сразу разрешает перезапись. Команда с интерактивным подтверждением:

```sh
cd "$HOME" && W=$(mktemp -d "${TMPDIR:-/tmp}/site-installer.XXXXXXXX") && git clone --depth 1 --branch main https://github.com/wwdewew1111-ctrl/SiteVSservice.git "$W/repo" && sh "$W/repo/install-reg-ru.sh"
```

Установщик повторно клонирует `main`, проверяет каталог, запрашивает `YES`, создаёт резервную копию в `$HOME/site-backup-...` и копирует сборку. Он не удаляет несовпадающие файлы, но перезаписывает совпадающие, включая `.htaccess`; проверь предупреждения в `DEPLOY_REG_RU.md`. Для нестандартного пути передай его аргументом скрипту. Не утверждай, что сайт на хостинге обновлён, пока это не подтверждено.

9. В итоговом ответе укажи изменения, результаты проверок, хеш коммита и статус публикации и развёртывания. После установки предложи проверить главную страницу, `/admin` и при необходимости обновить кэш браузера. Если что-то не проверено — прямо сообщи об ограничении.
